## What this run found

The last report handed me one instruction: *take the row ladder — declare the `w:trHeight` the 0.75 pt
ladder already lands on.* I took `18_displacement` (worth 54.0 clean documents in
`classpick.py --leverage`, more than the next two checks together) because that lead was inside it, and
the first thing I did was test whether it was true. It was not — and neither was the finding that had
falsified it in November. Both are now measured in Google, on one document, from the exported PDF's own
text positions.

### The page, the engine and the renderer, on `320_balance_sheet_statutory`

| | |
|:--|:--|
| the page's own row pitch (corpus PDF) | **14.00 pt** |
| Google's pitch for our `.docx` | **15.00 pt** |
| drift | **+1.00 pt per row, accumulating** — 21 rows, which is the `med_dy` the store has recorded since 25 Nov |

Four renders, one attribute changed each time:

| probe | change | Google's row pitch |
|:--|:--|--:|
| base | none | 15.00 pt |
| A | row `w:hRule="atLeast"` → `"exact"` | **15.00 pt** — not read at all; the render is identical to base |
| B | cell `w:line` 0.5 → 14.00 pt exact | **20.74 pt** — honoured, one way up only |
| C | per-row `w:line` ladder, 3 … 15 pt | 15.63 … 20.74 pt, monotone |

`w:hRule` is dead in Google. `w:line` is live — which answers the open question the 25 Nov falsification
left, in its own words: *"if Google still drifts, `w:lineRule` is not honoured and the lever is not a
number."* The lever is a number.

### `w:trHeight` **is** read — the November refutation refuted itself

That falsification declared **292 twips = 14.60 pt** and saw no change. That value is a no-op:
`0.75 × (round(14.60 / 0.75) + 1)` is **15.00**, the same rung the engine was already on. It could not
have produced a change, so "the declaration is absorbed by the content" was never supported by its data.

Three declarations in one render, the prediction written down before running it:

| declared `w:trHeight` | predicted | **measured** |
|--:|--:|--:|
| 300 tw (15.00 pt) | 15.75 | **15.75** |
| 280 tw (14.00 pt) | 15.00 | **15.00** |
| 260 tw (13.00 pt) | 13.50 | **13.50** |

### The fix that works, and the defect that stops it

14.00 pt is not on Google's 0.75 pt grid, so no single declaration reaches it — but each row may pick its
own rung, and two at 14.25 plus one at 13.50 average 14.00 exactly. Greedy per row against the page's
cumulative edge, the error stops accumulating instead of growing. Built into the row emitter behind
`p2w.rowresidue`, converted, rendered in Google:

| | base | engine build |
|:--|--:|--:|
| `med_dy` over the table rows | +10.30 | **-0.70** |
| every table row | +0.30 … +13.30 | **-0.95 … -0.45** |
| the line at the foot of the page | -0.16 | **-18.16** |

**Reverted, not committed, for a measured reason:** `worst_dy` is 18.16 pt, the document still fails
`18_displacement`, and no document moves.

### What the failure found — and it reorders the work

The line that broke is the one that was right by luck. In the base the engine's own flow is **18 pt short**
at the foot of that page and the row ramp put the line back: two errors cancelled on one line, and
`worst_dy` has been reading the cancellation, not the page. So **the flow after a ruled table must be fixed
first**; the residue fix then lands on top of it. That is one number in the paragraph placement, and it is
written down with the algorithm, the clamp and the three ways it can lose documents in
`FINDINGS/18-displacement-ROW-HEIGHT-IS-CONTENT-DRIVEN-26NOV-fixer.md`.
