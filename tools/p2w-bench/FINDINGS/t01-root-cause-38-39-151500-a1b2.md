# Root cause of t01_word_accuracy on 38_faux_bold_italic_synthesised and 39_small_caps_letter_spacing

Measured 21 Nov 2026 in this sandbox. Engine built from the clone at head
(`bash tools/p2w-bench/build-engine.sh`, JDK 17 fetched from Adoptium, 40 s compile),
`ConvertOne` on the corpus PDF, `tools/p2w-bench/verify_txt.py` unmodified in the shared
tree. 211 of the corpus PDFs were fetched (the `corpus-v1` release ships four zips, not
per-file PDFs; 211 PDFs unpacked, not 213 — the two missing ones are not either document).

Both documents reproduce their published scores exactly: 38 → t01 98.0, t07 6/5;
39 → t01 97.4, t12 2.

## 3. 39_small_caps_letter_spacing — the threshold rule, and why no writer change closes it

### The engine's rule

    app/src/main/java/com/kavopdf/app/engine/PdfToWord.java:4305
        float gs = g.sizePt > 0f ? g.sizePt : Math.max(1f, Math.round(g.size));
    app/src/main/java/com/kavopdf/app/engine/PdfToWord.java:4308
        && (gap > gs * 0.18f || gap < -gs * 0.6f)
    sibling copy used for the .docx runs:
    app/src/main/java/com/kavopdf/app/engine/PdfToWord.java:5529 (in runsOf())

Instrumented on a copy (debug print at the insertion site, `-Dp2w.gapdbg=1`), the values
the rule actually sees on the title line are:

    insert gap=2.0019608 gs=11.0 prev=H next=E psize=11.7 gsize=11.7
    insert gap=1.2009506 gs=6.0  prev=S next=T psize=6.24 gsize=6.24

`gs` is **11.0, not 11.7** — it is the text-space font size (`sizePt`), and the page scales
the font by 1.064 through the text matrix. The drawn letter gap is 2.00 pt and the
threshold is 0.18 × 11.0 = **1.98 pt**: the engine misses by 0.02 pt (1 %) and shatters the
heading into `T H E M Y S O R E`. The small-caps lines are 1.20 pt against 0.18 × 6.0 =
1.08 pt and shatter the same way. Every gap on the title line is exactly +2.000 pt — it is
uniform tracking, not a word gap.

### Measured: the reference rewards the wrong file

A hand-corrected .txt — the title once, `NOTICE TO MEMBERS`, `ELECTION OF THE MANAGING
COMMITTEE`, `ESTABLISHED 1886 • NO. 4, KRISHNARAJA BOULEVARD, MYSURU 570 005` — is the file
a reader would want. Scored by the unmodified checker:

| 39 .txt | t01 | t12 | t03 |
|---|---:|---:|---:|
| engine's .txt | 97.4 | 2 | pass |
| hand-corrected .txt | **58.2** | **17** | fail (my file used U+2014 where this PDF declares the dash as U+037E — my file's fault, not the engine's) |

The prior run's 58.5 / 22 is reproduced within the difference of my hand edit.

### Measured: a narrow engine change makes it worse

One-line candidate — threshold on the **rendered** size instead of the text-space size:

    -  float gs = g.sizePt > 0f ? g.sizePt : Math.max(1f, Math.round(g.size));
    +  float gs = g.size > 0f ? g.size : Math.max(1f, Math.round(g.size));

(on a copy, at :4305 and :5529). 0.18 × 11.7 = 2.106 > 2.00, so the title un-shatters:

| 39 .txt | t01 | t12 |
|---|---:|---:|
| before (head) | 97.4 | 2 |
| after this change | **78.8** | **14** |

The .txt gets better (`THE MYSORE CHAMBER OF COMMERCE AND INDUSTRY`, twice — hidden 1 pt
text layer + visible glyphs) and the score gets 18.6 points worse, because the reference
expects the shattered single letters. The small-caps lines still shatter (0.18 × 6.24 =
1.12 < 1.20), so the change is partial anyway.

**Verdict for 39: the reference's word-boundary rule is the thing that is wrong.** The
engine's 0.18 rule has a real, separate defect (it reads `sizePt`, 1 % below the drawn
tracking) that must not be fixed before the reference is fixed, or it costs 18.6 points.

## 4. 38_faux_bold_italic_synthesised — what fails, and which side

* `t01_word_accuracy` 98.0 — the reference's `get_text()` counts the faux-bold fill twice
  for both headings: 201 words against a .txt carrying 197.
* `t07_symbol_counts` source=6 txt=5 — the same duplicate: the em dash U+2014 exists twice
  in the reference (one per fill copy) and once in the .txt. The source's other non-ASCII
  is `•` ×3 and `;` U+037E ×1, both matched.

Both charges are the reference's. But measuring it turned up a **real engine defect that
the reference's double count hides**: the .txt carries the heading once and the subtitle
**twice**. The engine has a glyph-level dedupe —

    app/src/main/java/com/kavopdf/app/engine/PdfToWord.java:3186  dedupe()
    app/src/main/java/com/kavopdf/app/engine/PdfToWord.java:3190
        for (int i = out.size() - 1; i >= 0 && i >= out.size() - 40; i--)

— and the window is **40 glyphs**. The heading is 24 glyphs, so its second copy is still
inside the window and is dropped. The subtitle is 78 glyphs, so when its second copy
arrives the matching glyph is 78 back, outside the window, and it survives. The .txt
therefore repeats the 78-glyph line and not the 24-glyph one.

Measured with the window widened to 200 (one line, on a copy):

| 38 .txt | engine head | engine + window 200 |
|---|---|---|
| subtitle copies in .txt | 2 | **1** |
| t01 vs stock reference | 98.0 | **93.0** |
| t07 vs stock reference | 6 / 5 FAIL | 6 / 5 FAIL |
| t01 vs reference with the duplicate line collapsed | 100 (pass) | 100 (pass) |
| t12 vs that reference | 11 FAIL | 1 FAIL |

So the engine fix is correct on its own terms and costs 5 points until the reference stops
counting the fill twice — the same trap as 39, one document over.

**This reference-side candidate is NOT defensible as written, and I measured why.** On 38
the page draws `380` twice in the same table row (x=248.5 and x=348.5, one line each in
`get_text()`), so a line-identical dedupe drops a real word: the source word count goes
201 → 186 but `380` goes 2 → 1, which is why the last row above shows t12 = 1 invented
word. The defensible rule is span-identical **and position-identical** (same text, x and y
within 0.1 pt), which keeps both `380`s and drops only the two fill copies. That version
was **not built** — it needs the dedupe inside `glyph_truth()`'s trace walk, which is a
larger edit than the slot allowed.

## What I could not measure

* Corpus-wide blast radius of either engine change. Only the two documents were converted
  and scored; a full 211-document pass was not run.
* The defensible span-position dedupe in `glyph_truth()` — not built. The 100.0 / t12=11
  row uses the line-identical version, which I know to be over-broad.
* Whether any other corpus document hits the 40-glyph dedupe window. The mechanism
  predicts it for any faux-bold / overprint line longer than 40 glyphs; not swept.
* A boundary rule for the reference built from the drawn space glyphs (the repair 39
  actually needs). My drawn-word reconstruction reads `THE MYSORE CHAMBER OF COMMERCE AND
  INDUSTRY ... 570 005` — i.e. the .txt's words — but it welds across line breaks in my
  scratch implementation, so it is evidence, not a measured checker score.
* 211 of the 213 corpus PDFs: the release ships zips, and two documents named in the brief
  (`411_nested_xobject_transforms`, `601_fillable_admission_form`, `77_arabic_rtl_document`)
  were out of scope for this task and were not converted.

## What would settle what is open

1. Build the span-position dedupe in `glyph_truth()` (same text, |Δx|,|Δy| < 0.1 pt) and
   re-score all five t01 documents plus a full 211-document pass, so the reference change
   carries a measured blast radius instead of an argued one.
2. Build the drawn-space-glyph boundary rule for the source side and score 39 against it;
   the rendered page in `39_witness_address_300dpi.png` is the arbiter.
3. Only after the reference is corrected, land the two engine changes (dedupe window, and
   `gs` from the rendered size) and measure the corpus delta, so the writer's real defects
   stop being masked by the reference's.
