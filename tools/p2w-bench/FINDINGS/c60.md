# `60_text_column_right_edge` — is the produced table really ~2.4x wider, or is the check misreading?

**28 Nov 2026 · read-only measurement slot · repo `kavopdf/app` @ depth-1 clone (HEAD as cloned) ·
engine built in-sandbox (`pod-prep.sh`: JDK 17, PDFBox-Android 2.0.27.0, 12 engine sources) ·
corpus fetched (`corpus-fetch.sh`: 214 PDFs, 213 scored, 0 missing)**

---

## VERDICT (one sentence)

**Instrument misread, with a second real sub-class that is not geometry: no failing document's produced
table is ~2.4x the source's — measured over the 39 of the 56 store-failing documents that have a table
on both sides the produced table is 1.000x the source width at the median and 1.342x at the maximum, and
the "+161.18 pt on a 112 pt column" that produced the 2.4x figure is the source's *masthead* right edge
(339.04 pt, a different object on the page) being filed into the table's 111.87 pt Description column by
the check's independent left-edge clustering — while the failures that survive the instrument fix are
real render differences caused by Google substituting a narrower face for the declared DejaVu (28 of the
56), not by table width.**

## 2. What the check actually compares — read from the source, not from a summary

`tools/p2w-bench/verify_google.py`, check 60 block, `:2624-2930`. `verify_txt.py` has **no** check 60
(`--list-checks` lists t01…t13 only) — this is a .docx-side check only.

| property | value (source) |
|---|---|
| what is measured | the **right edge of a text column**, where a column is a cluster of **left** edges (`b[0] - seed <= 10`, `columns()`, `:2739-2770`) holding at least `max(3, 5 % of body lines)` lines |
| "right edge" of a column | the **widest line's** `bbox[2]` in that cluster (`edge()`, `:2772-2816`), i.e. the max, not a percentile |
| units | PDF points, PyMuPDF page space (top-left origin), per page |
| bands | lines whose box is inside the top/bottom `BAND = 0.06 × page height` are dropped (`:2753-2754`) |
| which side | **both** edges come from the text layer; the render's edge is compared **to the source's edge**, not to a page margin, not to a text frame |
| reference | the **source PDF** — the produced `.docx` is never read; only a rendered PDF of it |
| tolerance | fail if `rg > rs + 6.0 + slack` (over) or `rg < rs - 8.0 - slack` (under); `slack` = the column's **median word width**, capped at `SLACK_CAP 40.0` |
| correspondence | a render line is filed under **the column of the source line it is the same line as**, matched on text with zero-width characters stripped (`render_columns()`, `:2830-2900`); if no text match, by nearest source left edge within 10 pt; otherwise it evidences no column |
| page-level net | `far` = ≥2 render lines further right than `source_max + 18 pt` (`:2932`) |

**The check never reads `w:tblW`, `w:tblGrid`, `w:tcW`, or any PDF rule / rectangle.** There is no table
object anywhere in its code path. It answers "does this column of text end where it used to", not "is
this table the width it was". So a table-width claim can never come out of check 60 directly — it can
only come out of a *mis-assignment* of a line to a column.

## 6. Where the "2.4x" came from, measured to the digit

The 2.4x is the arithmetic of a **mis-assigned line**, and I reproduced both halves of it.

**The charge (recorded, Google).** On `gst-invoice-3line-items` the Description column starts at
`x = 62.92`. Its widest line in the source is `MS Hex Bolt M10 x 60mm, zinc plated` at `right = 174.79`,
so the column is **111.87 pt** wide. The pre-fix instrument charged `+161.18 pt`:

    174.79 + 161.18 = 335.97      (335.97 − 62.92) / 111.87 = 2.441x

That is the "2.4x widening" in `ATTEMPTS.json` (`13:41`): *"+161.18 pt on a 112 pt source column is a
2.4x widening"*. It is a ratio between **one small table column and the right edge of the masthead**.

**The object at 335.97 (measured by me, first-hand).** Dumping the page's text runs with left edge in
[55, 80] pt:

```
SOURCE                                        LO RENDER
left= 73.69 right= 339.04  "SUNRISE INDUSTRIAL FASTENERS PVT. LTD."   left= 73.80 right= 338.90  same
left= 73.69 right= 333.72  "GSTIN 06AASCS7788L1ZB · PAN … · CIN …"     left= 73.80 right= 322.31  same
left= 62.92 right= 174.79  "MS Hex Bolt M10 x 60mm, zinc plated"       left= 63.50 right= 173.68  same
```

The masthead is a company address block sitting **above** the table. It is not a table cell.

**The mechanism.** `columns()` buckets by left edge with a **10 pt** window, and source and render are
bucketed **independently**. The masthead's left edge is `73.69`; the Description column's is `62.92`.

    source:  73.69 − 62.92 = 10.77  >  10   -> masthead is its own column
    render:  73.50 − 63.75 =  9.75  <= 10   -> masthead joins Description   (Google, recorded)
    LO:      73.80 − 63.50 = 10.30  >  10   -> stays separate (which is why the proxy never sees this)

Description's "widest line" then became the masthead's 335.97 instead of the goods line's 173.68, and
the check charged the difference. **The verdict turned on 0.55 pt of left-edge position** — and on which
renderer you measured, which is why the LO proxy passes this document and Google fails it.

**Reproduced independently, in the proxy, on two more documents** (`probe60.py`, my own
re-implementation of the check's arithmetic run twice — once bucketing the render by its own left edges
as the pre-fix code did, once filing render lines under their source line as HEAD does):

| document | column left | source edge | pre-fix render edge | pre-fix delta | HEAD render edge | HEAD delta |
|:--|--:|--:|--:|--:|--:|--:|
| `purchase-order` | 428.30 | 449.71 | **552.68** | **+102.98 OVER** | 450.26 | **+0.56 pass** |
| `delivery-challan` | 422.76 | 473.53 | **550.94** | **+77.41 OVER** | 472.82 | **−0.71 pass** |
| `79_inr_indian_digit_grouping_table` | 323.10 | 372.37 | 417.69 | +45.32 (inside slack) | 370.30 | −2.07 |
| `gst-invoice-3line-items` | 62.92 | 174.79 | 173.68 | −1.11 (no artifact in LO) | 173.68 | −1.11 |

`+102.98` and `+77.41` are the recorded `+103.36` and `+77.21` to within the 0.10-vs-0.06 band constant
the older probe uses — the same artifact, on the same column, reproduced from scratch. And the implied
"multiplier" is not constant across documents: **2.441x** on gst-invoice, **2.525x** on delivery-challan,
**5.809x** on purchase-order. A real table-width defect would be one number; this is a foreign object's
right edge divided by whatever column happened to swallow it.

**The fix for this half is already in the tree** (`render_columns()`, `verify_google.py:2830`, landed
14:57 as `kept`, +3 documents), and its docstring names this exact document and this exact 161.18.

**A trap for the next run:** `tools/p2w-bench/edgeprobe.py` — the tool that produced the 2.4x number —
still buckets both sides independently (`:74-79`) and still uses `BAND = 0.10` where the check uses
`0.06`. Re-running it today will "confirm" the 2.4x again on a document the check now passes. It is a
pre-fix instrument and should be read as history, not as a probe.

## 7. The half that is real, and is not geometry

28 of the 56 declare a **DejaVu** face in the `.docx` (measured from `w:ascii` in `word/document.xml`):
`301, 302, 310, 311, 312, 313, 316, 317, 318, 321, 322, 323, 335, 340, 342, 343, 344, 352, 360, 363,
365, 370, 371, 373, 381, 383, 393, 406`. Google has no DejaVu, substitutes Arial, and Arial's advances
are narrower — so the render's widest line genuinely lands short of the source's and 60 fires **UNDER**.
That is a true difference between the source and the Google render. It is not a table-width defect: the
tables on those documents measure 0.949x–1.042x, and on `313` there is no table on either side at all,
while on `302` the offending line (`x = 28.00`, source right edge 543.74) spans the whole page and not a
cell. My own check of the faces agrees with the recorded finding:

```
313_power_of_attorney  | source faces: DejaVuSerif, DejaVuSerif-Bold | docx declares: DejaVuSerif
302_radiology_report   | source faces: DejaVuSans, DejaVuSans-Bold…  | docx declares: DejaVuSans, DejaVuSerif
gst-invoice-3line-items| source faces: LiberationSans, -Bold       | docx declares: Arial
```

So the class is **mixed in cause, uniform in geometry**: one part instrument artifact (now fixed), one
part real face-metric divergence (a genuine render difference, with a real, measured, currently blocked
lever), and **no part** that is a too-wide table.

## 8. What would go CLEAN, and what the fix is

* **Ceiling: 5 documents.** Only 5 of the 56 fail nothing but check 60 — `302_radiology_report`,
  `313_power_of_attorney`, `316_contract_with_schedules`, `321_auditors_report`,
  `79_inr_indian_digit_grouping_table`. The other 51 carry other failures and cannot be made CLEAN by
  any change to 60. (Consistent with `SHAPE-ANCHOR-1334-B1.md`'s 4-document list, which predates `79`
  entering the solo set.)
* **Of those 5, 4 have a measured lever** — the Verdana face declaration, measured through Google on
  `313/302/316/370/321`: 60 PASS 5 of 5 — **and it costs `53_embedded_faces` on all 12 documents
  tested** (recorded, `ATTEMPTS.json` 13:38). `79` is not in that tested set, so whether it flips is
  **not stated** in any record I read.
* **The instrument half is already fixed.** No further code change to 60 is warranted by anything I
  measured: the bucket artifact is closed at HEAD, and the 9 documents that still fail in the proxy fail
  on text advances with correct table widths.
* **The fix is therefore not a table fix at all.** Nothing in `DocxWriter` that writes table geometry
  (`w:tblGrid`, `w:tcW`, `w:tblW`) should be touched for this class — the produced grids reproduce the
  source grids to ≤0.7 pt on the documents where the check fires hardest. The open problem is a face
  whose metrics Google has *and* that `53_embedded_faces` will accept.

## 9. What I could not do, said plainly

**No live Google render.** Google Docs is ground truth and I did not measure it. There is no
file-staging route from this sandbox: `GOOGLEDRIVE_UPLOAD_FILE` / `GOOGLEDRIVE_RESUMABLE_UPLOAD` take a
`file_to_upload.s3key` produced by a platform `upload` step that this session does not have, and
`GOOGLEDRIVE_UPLOAD_FROM_URL` needs a public HTTPS URL for the `.docx` that nothing here can publish.
Every "Google store" number above is the recorded verdict in `RATCHET-GOOGLE.json` / `ATTEMPTS.json`,
read as data — not a measurement I made. Every LibreOffice number is labelled proxy.

**What that does and does not weaken.** The central claim is renderer-independent: the produced table
width is read from the `.docx` OOXML (`w:tblGrid` in twips), which is the width Google lays out — no
renderer is involved, and no renderer can change it. The claim that does depend on a renderer is
"the render's widest line sits at x" — and there I used LibreOffice and said so.

**Not measured by me:** whether `79_inr_indian_digit_grouping_table` flips under the Verdana lever;
whether the 47 proxy passes are Google passes (only `gverify` can say).
