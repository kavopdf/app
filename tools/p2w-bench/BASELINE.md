# Google-render baseline

Every document, measured by `verify_google.py` against the PDF that Google Docs
itself exports. A document passes only when every check passes.

The instrument: the docx goes to Drive, Drive converts it to a Google Doc, that
document is exported as PDF, and the export is compared to the original. See
`VERIFY-GOOGLE.md` for the pipeline and `verify_google.py` for the checks.

Newest rows were measured with engine **3651553** (v3.53.12). Every row carries the commit it
was measured with, because a score without a commit cannot tell a fix from a stale build.

This file is written by the hourly baseline cron. Rows are never deleted; a
re-run of a document replaces its own row.

A verdict of **CLOSED-UNFIXABLE** marks a document whose remaining failure is class
`20_within_10pt`, closed on 10 Nov: Google Docs has no exact line spacing, so it re-reads
`w:line` as a multiple of the paragraph mark's natural line height and no line box can be
placed where the page drew it. The measurement and the proof are in `REMAINING-DEFECTS.md`
under "Class 20_within_10pt — CLOSED UNFIXABLE". The score and the failed checks are left
as measured; only the verdict is closed.

## The `universe` column — read it before quoting a score

Every row says which set of checks it was counted out of. `u59` means the 59-check
instrument; `u57` means the live one. A score is a count of passes, so it is a count
*of something*, and two counts of different things cannot be compared, subtracted or
averaged. `ratchet.py` refuses to gate a row whose stamp disagrees with
`verify_google.py --list-checks`, and `record.py --audit` refuses to aggregate rows
that disagree with each other.

**All 211 rows in this file are `u59`, and the live instrument is `u57`.** On 13 Nov
the verifier retired `02_text_run_count` and `56_rtl_runs` and replaced
`20_within_10pt` with `20_line_placement`. The stores were never told: every row went
on reading `x/59` and `RATCHET.json` recorded `out_of: 59` while carrying a universe
list of 57 ids. Nothing in the pipeline compared those two numbers against the
verifier, so the two-check drift was arithmetically invisible — `ratchet.py` was
comparing the store's denominator against the store's denominator.

- **measured universe `u59`** — 59 checks, sha `d0388da5166d`, from
  `RATCHET-20261113-062943.json`, the archive of these same 211 marks taken at 06:29
  on 13 Nov.
- **live universe `u57`** — 57 checks, sha `55d390bbb7d6`, from
  `verify_google.py --list-checks` today.
- **delta** — `−2`: `−02_text_run_count −20_within_10pt −56_rtl_runs +20_line_placement`.

(Deliberately a list, not a table: every reader of this file counts `| ` rows to know
how many documents there are, and a second table in it would inflate that count.)

### What is still readable, and what is not

These rows were **not re-measured**, and no score in this table has been restated.
What can and cannot be recovered from them:

- **Readable.** The score and the failed list are exactly what the 59-check
  instrument reported, and remain valid as a record of that measurement. 196 of the
  211 rows name a retired check in `failed checks` (190 `20_within_10pt`, 111
  `02_text_run_count`, 10 `56_rtl_runs`); for the two *dropped* checks that is
  harmless — a dropped check simply stops counting.
- **Unreadable — every one of the 211 rows.** `20_line_placement` replaced
  `20_within_10pt`; it is a different measurement (median displacement relative to
  the page's line pitch, not a fixed 10 pt window) and it has never been run on
  these documents. So each row's score under `u57` is fixed only to within one
  check: `bounds_under_live` in `RATCHET.json` carries the exact interval per row,
  all of width 1. No row can be moved to `u57` without measuring it.
- **No row's verdict can be trusted either way.** All 211 read FAIL, and none fails
  only retired checks, so no document can silently become a PASS on the arithmetic
  alone — but a document could pass `20_line_placement` and lift by one check, or
  fail it and drop by one.

A `u59` row is therefore evidence about the 59-check instrument and nothing else. To
put a document on the live instrument, measure it: `record.py` stamps `u57` on the
row it writes, and `ratchet.py --recut --reason "…"` re-marks it, archiving the old
mark inside the new one instead of overwriting it.

## Reopened 2026-11-10

90 rows were marked CLOSED-UNFIXABLE, most of them on the single claim that Google Docs has
no exact line spacing. That claim was tested and is false. Documents written with `w:line`
at 240, 360 and 480 twips came back from Drive at 11.3, 17.1 and 22.8 pt: proportional,
monotonic, honoured, at about 95 % of the value asked. The classes are open again.

`20_within_10pt` alone touches 36 of the first 41 documents measured, so this is the largest
open class in the corpus. The measurement lives in `calibrate.py`; the fix it implies is a
multiplier of 1/0.95 where the engine writes the line height.

## Re-baselined 2026-11-10 - the verifier now carries 58 checks

The verifier grew from 31 to 58. Twenty-seven were added in two audits that asked what
the comparison actually catches and the answer was: position well, everything else
shallowly. Fonts and colours were compared as sets rather than per span, images and links
as counts rather than by position or target, and stroked lines were not read at all -
which is every table border in the corpus, and the defect reported by eye as 'the table
border is drawn over the text'.

Scores from an older verifier are not comparable with these, so every score cell is
empty again and the whole corpus is being re-measured. The old table is kept unchanged as
BASELINE-31checks.md.

The denominator is whatever `verify_google.py` prints - 58 today. Rows written by an
older verifier keep their own denominator, and `ratchet.py` compares only the checks that
existed at both marks, so adding a check never reads as a regression on every document.
